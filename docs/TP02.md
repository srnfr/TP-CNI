## Exposons avec un LoadBalancer

Exposons le déploiement avec un Load Balancer et notons la traduction de port :
```shell
kubectl expose deployment hello-world --type=LoadBalancer --port=80 --target-port=9898
```

Initialement *pending*, attendons que le Load Balancer obtienne une IP publique, puis récupérons-la automatiquement :
```shell
kubectl wait --for=jsonpath='{.status.loadBalancer.ingress[0].ip}' service/hello-world --timeout=5m
LOAD_BALANCER_IP=$(kubectl get service hello-world -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
echo "$LOAD_BALANCER_IP"
```

Visitons le site web avec notre navigateur.

Depuis le terminal CodeSpaces ou une station Linux, vérifions que le Load Balancer distribue bien les requêtes en lançant plusieurs appels avec `curl` :
```shell
for i in {1..100}; do
    curl -s "http://${LOAD_BALANCER_IP}" | jq '.hostname'
done | sort | uniq -c
```

Constatons l'adresse publique, le `NodePort` alloué et les Endpoints attachés au Service :

```shell
kubectl get svc hello-world -o wide
kubectl get endpointslice -l kubernetes.io/service-name=hello-world -o wide
```

Les commandes `kubectl get svc hello-world -o wide` et `kubectl get endpointslice -l kubernetes.io/service-name=hello-world -o wide` produisent respectivement les extraits suivants :

```text
NAME          TYPE           CLUSTER-IP     EXTERNAL-IP      PORT(S)        AGE   SELECTOR
hello-world   LoadBalancer   10.190.2.246   68.183.242.213   80:31917/TCP   85s   app=hello-world
NAME                ADDRESSTYPE   PORTS   ENDPOINTS
hello-world-pd8g9   IPv4          9898    10.180.0.207,10.180.0.156,10.180.0.24 + 2 more...
```

Le Service possède donc trois frontends utilisables : l'adresse publique `68.183.242.213:80`, la `ClusterIP` `10.190.2.246:80` et le `NodePort` `31917` sur les adresses des Nodes. Tous conduisent aux cinq backends qui écoutent sur le port `9898`.

### Identifions le comportement du Load Balancer DigitalOcean

L'offre de balanceurs de charge de DigitalOcean a évolué au fil des années. Le choix entre les deux offres est actionnable au moyen de l'annotation `service.beta.kubernetes.io/do-loadbalancer-type`, que nous renseignons avec l'une des deux valeurs suivantes :

* `REGIONAL` crée un Load Balancer HTTP avec terminaison de connexion et donne accès aux fonctions applicatives telles que la terminaison TLS, HTTP/2 et les sessions persistantes par cookie ;
* `REGIONAL_NETWORK` crée un Load Balancer réseau *pass-through* de niveau 4 pour TCP et UDP et conserve nativement l'adresse IP source du client.

Depuis DOKS `1.33.1-do.0`, `REGIONAL_NETWORK` est le choix par défaut lorsque l'annotation est absente. Sur les versions antérieures, la valeur par défaut était `REGIONAL`. La [documentation DigitalOcean sur les Load Balancers DOKS](https://docs.digitalocean.com/products/kubernetes/how-to/configure-load-balancers/#load-balancer-type) détaille ces possibilités.

Affichons le type de Load Balancer créé par DigitalOcean et la politique de trafic externe :

```shell
kubectl get svc hello-world \
    -o jsonpath='{.metadata.annotations.service\.beta\.kubernetes\.io/do-loadbalancer-type}{"\n"}{.spec.externalTrafficPolicy}{"\n"}'
```

La commande `kubectl get svc hello-world -o jsonpath=...` précédente produit dans ce TP :

```text
REGIONAL_NETWORK
Cluster
```

Un Load Balancer réseau régional (`REGIONAL_NETWORK`) achemine les paquets TCP/UDP sans terminer la connexion et conserve nativement l'adresse source du client. Le terme *pass-through* ne permet toutefois pas, à lui seul, de conclure que l'adresse de destination reste inchangée. La [documentation DigitalOcean](https://docs.digitalocean.com/products/kubernetes/how-to/configure-load-balancers/#network-load-balancer) distingue ce type du Load Balancer régional avec terminaison (`REGIONAL`), qui termine la connexion TCP du client et ouvre une connexion TCP distincte vers le backend.

La terminaison TCP ne doit pas être confondue avec la terminaison TLS. Un Load Balancer `REGIONAL` configuré avec un certificat peut terminer et déchiffrer TLS. En mode TLS *pass-through*, il ne termine pas TLS et transmet les octets chiffrés au backend, mais il reste un proxy qui termine les connexions TCP de part et d'autre.

Dans le cluster de ce TP, c'est la capture sur `eth0` qui apporte l'information supplémentaire : le paquet arrive sur le Node avec `68.183.242.213:80`, l'IP Publique du LB, comme destination. On peut donc conclure que, pour ce flux observé, DigitalOcean a dirigé le paquet vers un Node sans effectuer auparavant de DNAT vers l'adresse du Node ou vers le `NodePort` `31917`.

Le fait que le trafic retour ne repasse pas par l'étage de répartition n'empêche pas le Load Balancer de sélectionner un Node de manière stable. Dans l'[architecture décrite par DigitalOcean](https://www.digitalocean.com/blog/load-balancer-scaling-to-1000000-connections), le programme Katran consulte d'abord sa table de connexions. Pour un nouveau flux, il calcule un hachage cohérent inspiré de Maglev à partir des informations du paquet, choisit un backend, puis enregistre ce choix. Tous les paquets du flux aller peuvent ainsi être dirigés vers le même Node sans que le Load Balancer ait besoin de recevoir les paquets retour.

Maglev et le retour direct remplissent donc deux fonctions différentes : Maglev rend la sélection du backend déterministe à partir du flux entrant, tandis que le *Direct Server Return* (`DSR`) permet au backend d'envoyer la réponse directement vers le client. C'est leur combinaison qui permet de répartir le trafic aller sans imposer un passage du trafic retour par l'étage de répartition.

### Vérifions comment Cilium représente le Service

Préparons les variables utilisées pour interroger l'agent Cilium d'un Node :

```shell
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
CILIUM_POD=$(kubectl -n kube-system get pods \
    -l k8s-app=cilium \
    --field-selector="spec.nodeName=${NODE}" \
    -o jsonpath='{.items[0].metadata.name}')
LOAD_BALANCER_IP=$(kubectl get svc hello-world \
    -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
CLUSTER_IP=$(kubectl get svc hello-world -o jsonpath='{.spec.clusterIP}')
NODE_PORT=$(kubectl get svc hello-world -o jsonpath='{.spec.ports[0].nodePort}')
```

Affichons le mode de remplacement de `kube-proxy` :

```shell
kubectl -n kube-system exec "${CILIUM_POD}" -- cilium status --verbose \
    | grep -E '^KubeProxyReplacement:|^  Mode:|^  Backend Selection:|^  - (NodePort|LoadBalancer):'
```

La commande précédente montre que Cilium fonctionne en mode `SNAT` et utilise Maglev pour choisir le backend :

```text
KubeProxyReplacement:   True
  Mode:                 SNAT
  Backend Selection:    Maglev (Table Size: 16381)
  - NodePort:           Enabled (Range: 30000-32767)
  - LoadBalancer:       Enabled
```

Ce Maglev est celui de Cilium et intervient après la sélection du Node par le LB. Il ne doit donc pas être confondu avec le mécanisme utilisé en amont par DigitalOcean. Pour un nouveau flux destiné au Service, Cilium hache son *5-tuple* — protocole, adresses source et destination, ports source et destination — puis utilise le résultat comme index dans la table Maglev du Service afin de sélectionner un Pod. Cette décision ne dépend donc pas de l'observation préalable d'un paquet retour. Les agents Cilium utilisent la même table et la même graine de hachage : un même *5-tuple* conduit au même backend, même si le paquet entrant est traité par un autre Node. Une fois le Pod choisi, l'entrée conntrack enregistre notamment son `BackendID` et permet de traiter les paquets suivants ainsi que les traductions inverses. La [documentation Cilium sur Maglev](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/#maglev-consistent-hashing) décrit cette sélection cohérente pour le trafic externe.

Affichons ensuite les frontends et leurs backends programmés dans Cilium :

```shell
kubectl -n kube-system exec "${CILIUM_POD}" -- cilium service list \
    | grep -A 5 -F \
        -e "${LOAD_BALANCER_IP}:" \
        -e "${CLUSTER_IP}:" \
        -e "0.0.0.0:${NODE_PORT}"
```

La commande précédente affiche les trois frontends et leurs backends :

```text

                                             2 => 10.180.0.156:9898/TCP (active)

                                             5 => 10.180.1.120:9898/TCP (active)

                                             2 => 10.180.0.156:9898/TCP (active)
                                             3 => 10.180.0.207:9898/TCP (active)
                                             4 => 10.180.1.93:9898/TCP (active)
                                             5 => 10.180.1.120:9898/TCP (active)
```

Vérifions que l'IP Publique du LB n'est portée par aucune interface du Node interrogé :

```shell
kubectl -n kube-system exec "${CILIUM_POD}" -- ip -4 -br address
kubectl -n kube-system exec "${CILIUM_POD}" -- ip -4 address show \

```

La première commande affiche les adresses du Node. La seconde ne produit aucune ligne, car `68.183.242.213` n'est affectée à aucune interface :

```shell
kubectl -n kube-system exec "${CILIUM_POD}" -- cilium bpf lb list \
    | awk -v frontend="${LOAD_BALANCER_IP}:80" \

```

Cette commande prouve que l'IP Publique du LB, absente des interfaces, existe comme frontend dans la map eBPF et qu'elle est associée aux cinq backends :


Le `NodePort` existe bien, car Kubernetes l'alloue par défaut au Service `LoadBalancer`, mais il n'est pas utilisé par le flux observé. Cilium reconnaît directement `68.183.242.213:80` comme frontend de type `LoadBalancer` et lui associe les cinq Pods. Le [kube-proxy replacement de Cilium](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/) effectue cette sélection et les traductions dans les maps eBPF.

### Observons une connexion complète

Depuis la VM Linux, ouvrons un shell de diagnostic dans les espaces de noms réseau du Node choisi précédemment :

```shell
kubectl debug node/"${NODE}" -it \
    --image=nicolaka/netshoot \
    --profile=sysadmin \
    -- bash
```

À l'intérieur de ce shell de diagnostic, capturons les paquets du frontend et des backends :

```shell
tcpdump -ni any -nn 'tcp port 80 or tcp port 31917 or tcp port 9898'
```

Depuis une seconde fenêtre ouverte sur la VM Linux, redéfinissons les variables, car elles ne sont pas partagées entre les terminaux, puis générons une nouvelle connexion :

```shell
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
CILIUM_POD=$(kubectl -n kube-system get pods \
    -l k8s-app=cilium \
    --field-selector="spec.nodeName=${NODE}" \
    -o jsonpath='{.items[0].metadata.name}')
LOAD_BALANCER_IP=$(kubectl get svc hello-world \
    -o jsonpath='{.status.loadBalancer.ingress[0].ip}')

curl -s "http://${LOAD_BALANCER_IP}" >/dev/null
```

Le Load Balancer peut sélectionner un autre Node. Si la capture reste vide, recommençons sur un autre Node. Dans ce cas, redéfinissons `NODE` et `CILIUM_POD` avec ce même Node dans les deux fenêtres. Les maps de Service sont distribuées sur les Nodes, mais les entrées NAT et conntrack d'une connexion donnée doivent être consultées sur le Node qui traite cette connexion.

Dans l'exemple observé, la commande `tcpdump` produit les quatre paquets suivants :

```text
eth0 In  IP 164.92.220.17.44024 > 68.183.242.213.80: Flags [S]
eth1 Out IP 10.170.0.5.44024 > 10.180.0.156.9898: Flags [S]
eth1 In  IP 10.180.0.156.9898 > 10.170.0.5.44024: Flags [S.]
eth0 Out IP 68.183.242.213.80 > 164.92.220.17.44024: Flags [S.]
```

La première ligne prouve que le paquet arrive sur `eth0` avec l'adresse du client `164.92.220.17` comme source et l'IP Publique du LB `68.183.242.213:80` comme destination. Le Node choisi est ici `node-3mzce7`, dont l'adresse privée est `10.170.0.5`.

Cilium choisit ensuite le Pod `10.180.0.156:9898`, situé sur `node-3mzceq`. Comme `externalTrafficPolicy` vaut `Cluster`, un backend distant du Node d'entrée peut être utilisé. Le mode `SNAT` de Cilium effectue alors deux traductions avant l'envoi sur `eth1` :

* la destination `68.183.242.213:80` devient `10.180.0.156:9898` ;
* la source `164.92.220.17:44024` devient `10.170.0.5:44024`.

Relevons dans la capture le tuple du client et celui du backend sélectionné. Dans les commandes suivantes, les valeurs correspondent à l'exemple précédent ; remplaçons-les par celles de notre propre capture. Affichons alors les entrées NAT correspondantes depuis la seconde fenêtre de la VM Linux :

```shell
CLIENT_TUPLE='164.92.220.17:44024'
BACKEND_TUPLE='10.180.0.156:9898'

kubectl -n kube-system exec "${CILIUM_POD}" -- cilium bpf nat list \
    | grep -F -e "${CLIENT_TUPLE}" -e "${BACKEND_TUPLE}"
```

Cette commande produit la paire de traductions suivante :

```text
TCP OUT 164.92.220.17:44024 -> 10.180.0.156:9898 XLATE_SRC 10.170.0.5:44024 Created=38sec ago NeedsCT=0
TCP IN 10.180.0.156:9898 -> 10.170.0.5:44024 XLATE_DST 164.92.220.17:44024 Created=38sec ago NeedsCT=0
```

Ces champs se trouvent après le tuple source/destination de chaque ligne. La première contient `XLATE_SRC 10.170.0.5:44024` : la source du client est remplacée par l'adresse privée du Node d'entrée. La seconde contient `XLATE_DST 164.92.220.17:44024` : la destination de la réponse est retraduite vers le client.

Affichons ensuite l'entrée conntrack du Service :

```shell
kubectl -n kube-system exec "${CILIUM_POD}" -- cilium bpf ct list global \
    | grep -F "${CLIENT_TUPLE}"
```

Cette commande produit notamment :

```text
TCP SVC 164.92.220.17:44024 -> 68.183.242.213:80 Flags=0x0013 [ RxClosing TxClosing SeenNonSyn ] RevNAT=51 BackendID=25 NatPort=0
```

L'entrée `SVC` enregistre le tuple initial de la connexion, du client `164.92.220.17:44024` vers le frontend `68.183.242.213:80`. `RevNAT=51` désigne la traduction inverse à appliquer à la réponse afin qu'elle reparte avec l'IP Publique du LB comme source. `BackendID=25` est l'identifiant interne du backend sélectionné pour cette connexion. Le tuple traduit est, quant à lui, visible dans les deux entrées NAT précédentes.

Revenons dans la première fenêtre, interrompons `tcpdump` avec `Ctrl+C`, puis quittons le shell de diagnostic avec `exit`. Depuis la seconde fenêtre de la VM Linux, supprimons enfin le Pod temporaire créé par `kubectl debug` :

```shell
DEBUG_POD=$(kubectl get pods \
    --field-selector="spec.nodeName=${NODE}" \
    --sort-by=.metadata.creationTimestamp \
    -o name \
    | grep "pod/node-debugger-${NODE}-" \
    | tail -n 1)
kubectl delete "${DEBUG_POD}"
```

### Synthétisons le chemin observé

Le type de Load Balancer utilisé assure la conservation de l'adresse source du client jusqu'au Node, mais le Pod voit ensuite `10.170.0.5`, l'adresse privée du Node d'entrée, comme source de la connexion.

La SNAT force la réponse du Pod à repasser par le Node d'entrée. Sur ce Node, ici `node-3mzce7`, Cilium applique les traductions inverses : la réponse quitte alors `eth0` avec `68.183.242.213:80` comme source et l'adresse du client comme destination.

Le Node route ensuite ce paquet vers le client par le réseau DigitalOcean et sa passerelle par défaut, sans le soumettre de nouveau à la décision de répartition du Load Balancer. Au niveau Ethernet, la trame utilise la MAC du prochain saut fourni par le réseau virtuel DigitalOcean. Cette MAC, souvent virtuelle dans un environnement cloud, ne permet pas de conclure qu'il s'agit d'une interface du Load Balancer ni que le trafic retour repasse par celui-ci. Le retour est ici de type `DSR` : il conserve l'IP Publique du LB comme adresse source, mais contourne son étage de répartition.

Le chemin complet observé est donc :

```text
client 164.92.220.17:44024
  └─> Load Balancer REGIONAL_NETWORK 68.183.242.213:80
      ├─ sélectionne node-3mzce7 comme Node backend
      └─ transmet le paquet sans terminer la connexion TCP
          └─> node-3mzce7
              ├─ eth0 reçoit 164.92.220.17:44024 -> 68.183.242.213:80
              └─ Cilium applique les traductions
                  ├─ SNAT : source remplacée par 10.170.0.5:44024
                  ├─ DNAT : destination remplacée par 10.180.0.156:9898
                  └─> node-3mzceq
                      └─> Pod 10.180.0.156:9898
                          └─> réponse vers node-3mzce7
                              └─ Cilium applique les traductions inverses
                                  ├─ source remplacée par 68.183.242.213:80
                                  ├─ destination remplacée par 164.92.220.17:44024
                                  └─> réseau DigitalOcean
                                      ├─ utilise la passerelle du Node comme prochain saut
                                      └─ retour direct sans nouvelle décision du Load Balancer
                                          └─> Internet
                                              └─> client
```

Cette première étude relie donc les trois niveaux du flux : DigitalOcean choisit le Node, la map LoadBalancer de Cilium choisit le Pod, puis les maps NAT et conntrack permettent d'assurer les traductions et le retour. Nous allons maintenant reprendre le déroulement principal du TP. La seconde section avancée appliquera les mêmes notions à un `NodePort` et à une connexion sortante de Pod.

## [AVANCE 2 sur 2] Comparons les observations Linux et eBPF

> [!NOTE]

>
> La première partie avancée a reconstitué un flux entrant via le Load Balancer. Cette seconde partie consolide ces notions sur deux flux plus simples : une requête vers le `NodePort` et une connexion sortante initiée par un Pod. Elle distingue également ce que montrent `iptables`, `nf_conntrack` et les maps eBPF de Cilium.

Le Service étant désormais de type `NodePort`, nous pouvons nous concentrer sur les traitements du Node sans faire intervenir le Load Balancer DigitalOcean. Commençons par vérifier les fonctions effectivement activées dans Cilium, générons les deux flux de test, puis comparons les différents plans d'observation.

Dans le cluster DigitalOcean, **kube-proxy replacement** de Cilium (KPR) et la masquerade IPv4 eBPF sont activés (`kube-proxy-replacement: "true"` et `enable-bpf-masquerade: "true"`) :

```shell
kubectl -n kube-system get configmap cilium-config -o yaml \
    | grep -E 'kube-proxy-replacement|enable-bpf-masquerade|enable-ipv4-masquerade|masquerade'
```

La commande `kubectl get configmap cilium-config`, filtrée par `grep` dans le bloc précédent, produit notamment :

```text
enable-bpf-masquerade: "true"
enable-ipv4-masquerade: "true"
enable-ipv6-masquerade: "true"
enable-masquerade-to-route-source: "false"
kube-proxy-replacement: "true"
kube-proxy-replacement-healthz-bind-address: 0.0.0.0:10256
```

Ces deux fonctions sont indépendantes : KPR prend en charge le load-balancing et la translation des services (`ClusterIP`, `NodePort` et `LoadBalancer`) dans les maps eBPF, tandis que la SNAT de sortie des Pods est également réalisée par eBPF. Les règles `iptables` et la table `nf_conntrack` restent utiles pour comparaison, mais elles ne constituent pas ici le chemin principal de la NAT Cilium.

### Fenêtre 1 — VM Linux et Node

Dans cette fenêtre, lançons les commandes `kubectl`, générons le trafic de test et inspectons ensuite le réseau du Node :

```shell
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')

CILIUM_POD=$(kubectl -n kube-system get pods \
    -l k8s-app=cilium \
    --field-selector="spec.nodeName=${NODE}" \
    -o jsonpath='{.items[0].metadata.name}')
```

Le nom de `CILIUM_POD` est valable dans la VM Linux. Il ne faut pas le réutiliser comme une variable à l'intérieur du Pod Cilium.

Générons d'abord une requête vers le `NodePort`, puis une connexion sortante depuis un Pod placé sur ce même Node :

```shell
NODE_PORT=$(kubectl get service hello-world -o jsonpath='{.spec.ports[0].nodePort}')
NODE_IP_PUBLIC=$(kubectl get node "${NODE}" \
    -o jsonpath='{.status.addresses[?(@.type=="ExternalIP")].address}')

curl -s "http://${NODE_IP_PUBLIC}:${NODE_PORT}" >/dev/null

kubectl run nat-check \
    --image=curlimages/curl \
    --restart=Never \
    --overrides="{\"spec\":{\"nodeName\":\"${NODE}\"}}" \
    --command -- sleep 300
kubectl wait --for=condition=Ready pod/nat-check --timeout=60s
kubectl exec nat-check -- curl -s https://api.ipify.org
```

Ouvrons ensuite un shell de diagnostic temporaire dans les espaces de noms réseau du Node. L'image `netshoot` fournit notamment `iptables`, `tcpdump` et les autres outils réseau utilisés dans ce TP :

```shell
kubectl debug node/"${NODE}" -it \
    --image=nicolaka/netshoot \
    --profile=sysadmin \
    -- bash
```

Une fois dans le shell de diagnostic du Node, affichons les règles NAT classiques présentes sur le Node :

```shell
iptables -t nat -nvL --line-numbers
iptables-save -t nat | grep -E 'CILIUM|KUBE|MASQUERADE|SNAT|DNAT' || true
```

Affichons ensuite les entrées de la table de suivi Linux en excluant le loopback et les destinations du réseau `10.0.0.0/8` :

```shell
awk '!/127\.0\.0\.1/ { for (i = 1; i <= NF; i++) if ($i ~ /^dst=/ && $i !~ /^dst=10\./) { print; break } }' \
    /proc/net/nf_conntrack || true
```

La commande `awk` précédente peut notamment afficher des flux avec l'IP publique du Node :

```text
ipv4     2 tcp      6 431997 ESTABLISHED src=159.89.104.122 dst=157.245.22.191 sport=51906 dport=443 src=157.245.22.191 dst=159.89.104.122 sport=443 dport=51906 [ASSURED] mark=0 zone=0 use=2
ipv4     2 tcp      6 431993 ESTABLISHED src=159.89.104.122 dst=157.245.22.191 sport=38018 dport=443 src=157.245.22.191 dst=159.89.104.122 sport=443 dport=38018 [ASSURED] mark=0 zone=0 use=2
```

`nf_conntrack` affiche le tuple déjà vu par le noyau. Avec la masquerade eBPF, il peut donc contenir l'IP publique du Node plutôt que l'IP originale du Pod. Il ne remplace pas la lecture des maps Cilium.

Quittons le shell de diagnostic avec `exit`, mais laissons `nat-check` tourner. Le nom du Pod temporaire, affiché par `kubectl debug`, commence par `node-debugger-${NODE}-`. Ouvrons alors une deuxième fenêtre de terminal dans la VM Linux. Les variables shell n'étant pas partagées entre les fenêtres, redéfinissons-les puis entrons dans le Pod Cilium :

```shell
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
CILIUM_POD=$(kubectl -n kube-system get pods \
    -l k8s-app=cilium \
    --field-selector="spec.nodeName=${NODE}" \
    -o jsonpath='{.items[0].metadata.name}')

kubectl -n kube-system exec -it "${CILIUM_POD}" -- bash
```

### Fenêtre 2 — Pod Cilium

La commande suivante est maintenant exécutée **à l'intérieur du Pod Cilium**. Elle ne commence plus par `kubectl exec` :

```shell
cilium bpf nat list | head
```

`head` limite l'affichage aux premières lignes. La commande précédente peut produire cet extrait de la table NAT :

```text
UDP IN 10.180.1.108:53 -> 10.170.0.5:58968 XLATE_DST 10.170.0.5:58968 Created=412sec ago NeedsCT=1
TCP OUT 10.170.0.5:44500 -> 10.170.0.4:4240 XLATE_SRC 10.170.0.5:44500 Created=866sec ago NeedsCT=1
UDP OUT 10.170.0.5:37436 -> 10.180.0.205:53 XLATE_SRC 10.170.0.5:37436 Created=652sec ago NeedsCT=1
```

`cilium bpf nat list` affiche les traductions présentes dans les maps NAT eBPF :

* `IN` et `OUT` indiquent le sens du paquet par rapport au Node ;
* `XLATE_SRC` indique une réécriture de la source, typiquement une SNAT de Pod vers l'adresse du Node ;
* `XLATE_DST` indique la réécriture inverse de la destination, généralement pour le paquet retour ;
* `Created` indique l'âge de l'entrée en secondes ;
* `NeedsCT=1` indique que l'entrée NAT est associée au suivi de connexion Cilium.

Le format général d'une paire de lignes issue de `cilium bpf nat list` est :

```text
TCP OUT <IP_POD>:33544 -> <IP_DESTINATION>:2181 XLATE_SRC <IP_NODE>:33544
TCP IN  <IP_DESTINATION>:2181 -> <IP_NODE>:33544 XLATE_DST <IP_POD>:33544
```

signifie que le paquet sortant a vu sa source `<IP_POD>` remplacée par `<IP_NODE>`, puis que la réponse a été réécrite vers le Pod.

Affichons ensuite les premières entrées de la table de suivi de connexion eBPF :

```shell
cilium bpf ct list global | head
```

`cilium bpf ct list global` affiche une table distincte de la table NAT. On y lit notamment :

* `IN`/`OUT` et le tuple IP/port de la connexion ;
* `expires`, le délai restant avant expiration de l'entrée ;
* `Packets` et `Bytes`, les compteurs de trafic ;
* `RevNAT`, l'identifiant d'une éventuelle traduction inverse de service ;
* `BackendID` et `NatPort`, les informations de backend et de port lorsqu'une traduction de service les utilise ;
* `SourceSecurityID`, l'identité de sécurité Cilium de la source.

La commande précédente peut produire cet extrait de la table CT :

```text
TCP IN 10.180.0.51:52666 -> 10.180.0.101:8081 expires=46597 Packets=0 Bytes=0 RxFlagsSeen=0x1b LastRxReport=46587 TxFlagsSeen=0x1b LastTxReport=46587 Flags=0x0013 [ RxClosing TxClosing SeenNonSyn ] RevNAT=0 SourceSecurityID=1 BackendID=0 NatPort=0
TCP IN 10.180.0.51:54112 -> 10.180.0.94:8080 expires=46888 Packets=0 Bytes=0 RxFlagsSeen=0x1b LastRxReport=46878 TxFlagsSeen=0x1b LastTxReport=46878 Flags=0x0013 [ RxClosing TxClosing SeenNonSyn ] RevNAT=0 SourceSecurityID=1 BackendID=0 NatPort=0
TCP IN 10.180.0.51:44434 -> 10.180.0.101:8081 expires=45827 Packets=0 Bytes=0 RxFlagsSeen=0x1b LastRxReport=45817 TxFlagsSeen=0x1b LastTxReport=45817 Flags=0x0013 [ RxClosing TxClosing SeenNonSyn ] RevNAT=0 SourceSecurityID=1 BackendID=0 NatPort=0
```

Une ligne avec `RevNAT=0`, `BackendID=0` et `NatPort=0` décrit généralement une connexion suivie sans traduction inverse de Service associée. Les valeurs peuvent varier selon le trafic existant sur le Node ; `head` ne montre qu'un échantillon des entrées.

Quittons le Pod Cilium avec `exit`, puis revenons dans la première fenêtre VM Linux. Supprimons le Pod de test et le Pod de diagnostic du Node :

```shell
kubectl delete pod nat-check
DEBUG_POD=$(kubectl get pods \
    --field-selector="spec.nodeName=${NODE}" \
    --sort-by=.metadata.creationTimestamp \
    -o name \
    | grep "pod/node-debugger-${NODE}-" \
    | tail -n 1)
kubectl delete "${DEBUG_POD}"
```

Résumons le rôle de chaque observation :

| Commande | Plan observé | Ce que nous pouvons en déduire |
|---|---|---|
| `iptables -t nat` | Règles Netfilter du Node | Les règles NAT classiques présentes, même lorsqu'elles ne constituent pas le chemin principal de Cilium |
| `/proc/net/nf_conntrack` | Suivi de connexion Linux | Les tuples vus par la pile réseau Linux |
| `cilium bpf nat list` | Maps NAT eBPF | Les réécritures de source ou de destination réalisées par Cilium |
| `cilium bpf ct list global` | Maps conntrack eBPF | L'état des connexions, le reverse NAT et le backend associé lorsqu'ils sont renseignés |

Cette comparaison complète la première partie avancée : une capture montre les paquets réellement présents sur les interfaces, tandis que les tables Linux et les maps Cilium expliquent les états et les traductions qui produisent ce chemin.

Pour approfondir le rôle des maps eBPF et le remplacement de `kube-proxy`, consultons les ressources suivantes :

* [eBPF Maps — documentation Cilium](https://docs.cilium.io/en/stable/network/ebpf/maps/) ;
* [Kubernetes Without kube-proxy — documentation Cilium](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/).
